## 三、核心命题：写记忆=价值判断任务（用户核心担忧的解答）

**用户担忧原文要点**：本地 27B「半残」、35B「不残但不聪明」，云端 GLM 600+B / DeepSeek 1000+B（MoE 激活 40-60B），本地模型写回云端记忆库会不会污染？

**分析与裁决**：
1. **写记忆≠生成任务，是价值判断任务**——27B 写流畅蕾姆对话没问题（实测在线），但「什么值得永久记住」的判断是云端与本地的真实差距所在。
2. **业界两流派（联网查证 1006）**：
   - **Mem0 派（主流）**：agent 不参与写决策，对话流水过独立提炼管线（原话 "keeps memory operations out of the agent's inference budget"）
   - Letta/MemGPT 派：agent 自编辑记忆——只对旗舰模型成立
3. **咱家现役架构已是 Mem0 派**：云端桥每天 21:00 GLM 日志提炼 cron（DIARY）=现成定稿层。
4. **三级写权限（裁决）**：
   - **L0** 纯本地不上云（敏感闲聊开关，用户可选）
   - **L1 ⭐推荐**：本地摘要推云→云端入库（详见 §四 v3）
   - **L2 本地模型直接写库：永久禁用**——半残模型的价值判断不可信
   - 读：随时可 /recall 只读，读不污染
5. **规模论证修正**：DeepSeek V4≈671B 总参/激活 ~37B（用户猜 40-60B 接近）；激活参数非能力线性度量——云端胜在判断力而非文笔，恰好支持「27B 管说、GLM 管记」分工。

## 四、Phase 1 设计演进三版（v3=终极形态，用户提出）

### v1（AI 初案，已废）：定时推原始对话
本地定时任务推当天对话→云端提炼。**用户否决理由（全对）**：9 点没开机=错过窗口；两天没开=攒账算不清；推了回执丢=重复推；本地云端两份账必然对不齐。

### v2（用户案，被 v3 迭代）：云端收件箱
推到云端仓库放着→云端自己定时消化→消化完删→本地不留账。补强=按天分块+覆盖式接收（同一天重推=覆盖，天然幂等防重）。**贡献被 v3 继承**：按天幂等、消化即删、多路触发。

### v3（用户终极案，⭐定稿）：本地摘要推云
**用户原话要点**：「在本地把摘要做好，直接把摘要推到云上去。之前是 N，现在是 1。回执就很好做了，推一个东西，成功就成功失败就失败，不行再推一次。**本地拿 API 的模型去整理摘要，跟云上是一个 API，不会拿本地模型去做摘要的**」。

**AI 判决=全盘采纳，生命线=摘要用 GLM API（闸门不丢，只是从云端搬到推送前）**。四连升级：
| 维度 | v1/v2 | v3 |
|---|---|---|
| 推送物 | 几十 KB 原始流水 | 1-2KB 摘要（N→1） |
| 回执 | 模糊/幂等但物大 | 单个小事务：成功/失败/重推 |
| 云端角色 | 收件+提炼（重活） | **降级记账员**（收摘要→入库，21:00 提炼 cron 省了） |
| 隐私面 | 全量对话上云 | **只有摘要上云**（原始流水可永不出本地，白送安全升级） |

**诚实账（已向用户交底）**：摘要仍需把当天对话喂 GLM，**token 消耗与原方案相同**；变的是时序解耦（与开关机无关）/推送物幂等/云机减负（4G 小马不再干提炼）/隐私面缩小。

## 五、Phase 2 设计：记忆中间件+测速（读桥不写桥）

**目的**：本地脑获得记忆宫召回（读），补「功能裸奔」短板。
**形态（待拍板二选一）**：
- A 常驻小代理：桌宠链路多一个进程（base_url 指代理→代理查 /recall 注入→转发 18080）——灵活但多一个保活件
- B 配置直指代理（同 A 但把代理当 llm 端点写死进 rem_localbrain.yaml）——零新进程观感，实质同物

**用户速度担忧与修正记录**：
- 用户原话要点：「不怕召回网速（几 KB-二十几 KB），怕云机性能不高+可能限速（猜 400 多 K）得实测；更担心本地生成 40 tok/s 还要解析云端几 K 文本」
- **AI 修正**：40 t/s 是生成速度；「解析」=prefill 是另一套账——128K 版实测 prefill **375.6 t/s**（读比写快 8 倍）；注入 3000 token≈8 秒（有感！担忧依然成立）
- **关键工程杠杆（现实锚教训同源）**：召回**注入位置**决定生死——放前缀=每轮缓存失效全量重读（每轮罚 8s）；放**末尾**（最新消息旁）=前缀缓存命中，只读增量。1005 智谱缓存全灭案同一物理定律。
- **实测三数（阶段二验收指标）**：①几 KB 跨 EasyTier 往返延迟（含云机 4G 响应）②注入 3-5K token 本地 prefill 秒数 ③注入尾部后多轮对话每轮增量耗时
- **EasyTier 现状**：ssh 公网通道实测云机可达 ✅；EasyTier 本地节点停着（要 UAC），p2p 史上零丢包

## 七、质量闸门（最新一轮讨论，mem0 血泪案背书）

**用户洞察**：本地学习会产生大量重复无意义碎片（反复询问），全量上云=垃圾账污染酒馆——酒馆聊天都是重点内容，碎片化无意义的东西推上去「酒馆就完了」。

**联网查证金矿**：mem0 官方仓库 Issue #4573——有人审计 10,134 条记忆，**97.8% 是垃圾**。教训：
- 前 20 天用 2B 小模型提炼、换 Claude 旗舰**并没有好转**——「**瓶颈在提炼提示词，不在模型**」
- 标准解法=提炼与入库之间加 **quality gate**（过滤心跳/cron 噪音/客套话）+防重提取 feedback loop
- 咱的转化：闸门前移到摘要 prompt 内（GLM 顺手输出密度评级）+done 清单反馈环（天生就有）

**密度闸门设计**：摘要 prompt 要求 GLM 同时输出 `substance_level: none/low/high`——none/low 的天只推标记云端跳过（垃圾日在门口盖戳退回）；high 才入库。垃圾日的 API 成本=一句「今日无实质内容」几分钱。

### 追加 1006 深夜②：云端存量记忆的寒暄防护（讨论完毕，裁决=搭车搞）

**用户问题**：云端也有垃圾——反复"你好/晚上好"不该进记忆。云端三份：摘要（反复堆晚上好不是事）/原始对话（不用管）/最近 20 条视野（稀释注意力）。优化空间不大（用户自述上云都有正事），要不要搞？

**AI 查实（ssh 云机读桥源码原文）**：
- 摘要 maybe_summarize：prompt 只有正面指令（保留人名数字承诺未完话题），**无负面指令（无忽略寒暄）**——链式继承（prev 进下段 prompt）是唯一永久化风险口子
- 日记 _condense_day：无显式闸门，文学体裁天然滤 + ≥2 条门槛——中低危
- 视野 40 条：滚动自愈——无永久危害
- 记忆宫：0.55 召回阈值硬挡，寒暄召不回——零危害

**裁决（用户三选一 → 选"搭车搞"）**：不立项不专门搞；Phase 1 施工时搭车在摘要+日记两处 prompt 各补一句负面指令（「纯寒暄、重复问候、无信息交换的内容忽略不计，不计入梗概」）——两行改动同次部署，把天然免疫升级为显式免疫。视野/记忆宫明确不动。依据：mem0 #4573 被过滤对象清单第一条即 generic acks（业界必选，咱靠自觉）。

**与本地摘要密度闸门的关系**：同一哲学两头焊死——本地闸门（substance_level）管新账、云端 prompt 补丁管存量账。
