# OPS-20260917d-显存圈地-限长分片与一键重启

> 背景用户问题：VMM 保留只涨不还，怕与本地大模型同卡时把 LLM 挤到硬盘；要求①回答"流式了还要不要限长"②桌面一键重启③"到底能不能圈死显存（预算 1.5G）"。

## 一、"能不能限制显存"的结论（2026-09-17 定案）

1. **Windows 消费级驱动没有进程级显存硬上限**（MIG/vGPU 是数据中心卡功能）。"圈死 1.5G"无原生旋钮。
2. **硬保证靠入口限长**：服务端 tts.cpp 对"病态超预算"文本块会退化成整段单次合成（`cosyvoice-tts.cpp` 单call回退路径，n_max_seq 不设防）——这是失控大缓冲把 VMM 池顶上去的元凶。代理层 500 字封顶后此路不通。
3. **软保险是 NVIDIA 官方开关**：`CUDA - Sysmem Fallback Policy`（驱动 536.40+，NVIDIA 控制面板 → 管理 3D 设置 → 程序设置 → 选 cosyvoice-server.exe）。显存不够时 TTS 的超量分配落系统内存（该次合成变慢）而不是把 LLM 挤出去。官方说明：<https://nvidia.custhelp.com/app/answers/detail/a_id/5490/~/system-memory-fallback-for-stable-diffusion>。用户手动设置（程序列表选 exe，设 Prefer Sysmem Fallback 或保持 Driver Default 均可）。
4. VMM 高水位机理定案见 REFERENCE §三：官方定性故意设计（[llama.cpp#4712](https://github.com/ggml-org/llama.cpp/issues/4712) closed-stale，无"用完即还"开关），源码核实 VMM 池 `free()` 只回退指针不还物理显存。

## 二、显存实测账（4060 8G，速度 1.15，单请求）

| 工况 | 合成耗时 | 显存（重启后 855 MiB 基线起） |
|---|---|---|
| 空载（模型+KV 装载完） | — | **855 MiB** |
| 51 字小段落（酒馆分段朗读常态） | 5.5s | **1345 MiB**（+490） |
| 250 字单发 | 12.6s | **1813 MiB**（+958） |
| 500 字单发 | 23.9s（197s 音频，RTF 0.12） | **1863 MiB**（+1008） |
| 1800 字分片 4 片拼接 | 88.9s（749s 音频，RTF 0.12） | **1917 MiB（仅 +54！）** |

要点：
- **+490 → +958 之间有台阶，250 以上进入 ~1.8-1.9G 平台**，不随字数线性涨；分片后 4 连发仅再 +54 —— 显存峰值跟"单片长度"走，与总长无关，封顶策略有效。
- 对用户 1.5G 预算：**日常段落工况 1.35G 放得下**；最坏 1.9G 超出 ~0.4G，由 NVIDIA fallback 阀门兜底（落内存不挤 LLM）。要严格压进 1.5G 可把代理切片上限降到 ~150 字，代价是拼接缝变密（韵律重置感）——**此难題已被 §四 v3.1 句级分片解决（80 字片实测 1.44G），见下**。
- 长 197s/749s 音频的"字/秒"偏慢（~2.5），与测试文本全是排比长句+大量句号停顿有关，非异常。

## 四、v3.1 句级分片（同日二改，2026-09-17 深夜）

用户指认"正常回复每句才 50-100 字，根本不该有 500 字直冲"，并点名复用旧伪流式档的切割规则。核实来源：
- **本地旧档**：`aiDocs\cosyVoice3\集成\长文本朗读流水线方案调研.md`（2026-09-03 归档）——语义分句按句号/问号/感叹号切勿硬切 50 字符；单段 ≤150-200 字符（CosyVoice 安全上限）；**2-3 字单段会出畸形音频必须合并**；**拼接处不加 0.1-0.2s 静音会爆音/断感**。配套 `伪流式TTS改造方案操作手册` 有 SentenceSplitter 类设计。
- **业界印证**（Deepgram [Text Chunking for TTS](https://developers.deepgram.com/docs/tts-text-chunking)/Shunya/AssemblyAI/stream2sentence 共识）：句边界切、词级切杀韵律、缓冲到边界确定再送合成。

**实现（proxy v3.1，文件不变仍为 cosyvoice-proxy-20260917b.py）**：句末标点（。！？!?；;\n…）分句 → 短句合并至单片 ≤TARGET=80 字 → 超长句在逗号级软切（回看 40 字找最后一个软标点，无则硬切）→ <10 字尾片并入前片 → 逐片合成、片间插 0.12s 静音、重组 RIFF。单次请求（≤80 字）仍走直通不拼。

**实测（基线 855 MiB）**：
| 工况 | 显存 | 速度 |
|---|---|---|
| 68 字（切 2 片） | 1389 MiB | 5.7s |
| **1800 字 → 29 片（全 ≤80）** | **1443 MiB** | 97s（820s 音频，RTF 0.118） |
| （对照）v3 的 500 字片 | 1863-1917 MiB | RTF 0.12 |

**结论：最坏情况显存峰值从 ~1.9G 压到 ~1.44G，正式进入用户 1.5G 预算内**；NVIDIA Sysmem Fallback 从"必需阀门"降级为"额外保险"。切片对速度几乎零损耗（RTF 持平），音质影响 = 每句自然换气 + 片间 0.12s 静音，反而更贴朗读节奏。未来可选项：代理层 markdown 清洗（旧档流水线第 1 步，#/*/代码块丢弃），现无需求未做。

## 五、用户问答存档

- **"流式了还会一口气 500/2000 字吗"**：不会。服务端 `--stream` 因 RIFF 假头 bug 已移除；酒馆"分段朗读"把回复按段落拆成多个小请求（几十字/个）——这是常态流量；代理句级分片只拦病态场景（手动点喇叭重读超长消息、模型单段巨长输出），拦到后自动切片拼接、内容零丢失。GPU 永远只见 ≤80 字的片。
- **"大模型 6G + 预留 0.7G，语音 1.5G 够不够"**：v3.1 后**够**——最坏情况（1800 字 29 片）实测 1443 MiB，日常 1.35-1.39G；NVIDIA fallback 阀门转为额外保险。开机流程：跑大模型前先双击桌面"重启语音服务"（10 秒，显存归零重起）。
