# CosyVoice‑3 你遇到的两个现象，GitHub大量人复现，属于已知bug
> 现象1：克隆生成音频，**混入参考干声的文本内容**，参考音频说“今天早上好”，生成出来开头/中间会蹦出“今天早上好”，再读目标文本。
> 现象2：随机蹦无关语气词、碎词、胡言乱语。

## 社区issue对应
1. issue#1735：zero‑shot克隆，生成音频随机胡言乱语，**同时会把参考prompt音频的文本漏到输出音频**，非必现，概率性触发。
2. issue#1833：fastapi/服务部署场景，`inference_zero_shot`，**prompt_text太长就会泄露参考音频的文字到输出**，大量部署者踩坑。
3. 流式接口尤其容易触发参考文本泄露；**非流式完整推理，泄露概率会低很多**。

> 重点：不是你的wav录音不干净，是推理链路的缺陷，官方ModelScope网页demo不会复现，本地部署（尤其自己封装API、伪流式）高频出现。

## 已经被社区验证有效的缓解方案（按优先级）
### ① zero‑shot克隆，不要填完整参考音频字幕（最关键）
`inference_zero_shot(prompt_text=xxx)`这个参数，**不要把参考音频完整一大段文字丢进去**。
- ❌错误：参考音频是“今天早上好”，`prompt_text="今天早上好"`，长prompt_text极易触发文本泄露进输出音频。
- ✅方案A：把`prompt_text`限制在**10‑14个字以内**，越短泄露概率越低。
- ✅方案B（很多开发者最终选择）：改用`inference_instruct2`接口，`prompt_text`固定填占位字符串：`You are a helpful assistant.<|endofprompt|>`，不再填入参考音频真实字幕，大幅抑制参考内容泄露问题。

> 注意：`inference_instruct2`依然传入`prompt_wav`参考音频，音色克隆效果保留，只是不再把参考音频的文字喂给模型。

### ② 参数层面，抑制随机乱蹦语气词、幻觉碎音
1. **固定随机种子**，每次推理设置同一个seed，减少随机幻觉输出。
```python
from cosyvoice.utils.common import set_all_random_seed
set_all_random_seed(42)
```
2. 降低flow推理的`temperature`，默认1.0，调到`0.6‑0.75`，随机性下降，乱蹦语气词会明显变少；代价是语音情感丰富度轻微降低。
3. **尽量避免流式分片生成做克隆**。你现在在做伪流式对接，zero‑shot克隆优先跑完整非流式拿到完整wav，**上层再做分片切割输出**，不要把zero‑shot推理本身开成流式，流式路径泄露bug最多。

### ③ 音频样本本身的硬性条件（兜底）
参考干声wav：16kHz、单声道wav，5‑8秒，人声干净无背景噪音，不要超过12秒。
样本本身质量差，会放大上面两个bug的触发概率。

### ④ 版本问题
Fun‑CosyVoice3‑0.5B‑2512这个权重，该泄露bug一直存在；官方没有完全修复，只有上面的规避手段。原版仓库的demo网页做了特殊处理，所以网页测是好的，本地写接口就踩坑。

## 对你做Open‑WebUI + CosyVoice伪流式对接的现实提示
1. 不要在流式chunk内部反复执行zero‑shot克隆。**一次请求只做一次音色提取，拿到speaker embedding，后续文本分片只用tts推理，不要再重复传prompt_wav**。重复送参考音频会极高概率触发参考内容泄露。
2. 不要使用`inference_zero_shot`做分片流式推理，上层业务自己把完整生成好的wav切片模拟流式输出，避开底层流式推理bug。
3. 如果还是偶尔蹦出参考音频片段，你的业务层可以加简单的音频后处理，把音频开头一小段截断0.2‑0.4秒，规避绝大多数泄露发生在音频开头的现象。

## 现实总结
这不是你代码写崩，是CV3本地部署一个广为人知的概率性缺陷，官方没有彻底修复，只能靠调用方式绕开。
- 最大元凶：zero‑shot接口传入**完整长prompt_text**；
- 次高危：底层开启流式zero‑shot推理；
- 临时最优路线：切换`inference_instruct2`，占位prompt_text，非流式推理，上层自己切分片模拟伪流式。

五、aiodns的问题
`aiodns` 是一个 Python 异步 DNS 解析库。它本身是一个中性的工具，之所以会“绕过”代理，是因为它的工作方式非常特殊。

### 🧐 它是什么：一个“抄近道”的DNS解析器

`aiodns` 是一个**异步**DNS解析库，它的核心特点是**不通过操作系统的标准DNS解析流程**（即不走 `socket.getaddrinfo` 这套API）。

*   **传统方式**：程序请求解析域名时，会通过操作系统的一个标准接口（`getaddrinfo`）去查询。如果你设置了VPN或TUN代理，它们通常会在这个层面“接管”你的DNS请求，让你能正常访问外网。
*   **`aiodns` 的方式**：它绕过了这个标准接口，通过自己的底层代码（基于`c-ares`库）直接与DNS服务器进行UDP/TCP通信。这就像你家门口专门修了一条“私人通道”直达DNS服务器，不经过社区主路。

### 🚀 它为什么能绕过你的代理？

你的TUN代理，其核心原理是在操作系统的网络层面建立一个虚拟网卡，所有网络请求（包括DNS查询）都会被引导至这个虚拟网卡，再由代理软件进行处理。

而`aiodns`“抄近道”的运作方式，恰好避开了这一机制：

1.  **不经过系统API**：代理通常需要劫持系统API（如 `getaddrinfo`）才能生效。`aiodns`绕过了这个API，代理也就无法“拦截”它的DNS查询请求。
2.  **直接UDP通信**：`aiodns`会直接向公共DNS服务器（如 `8.8.8.8`）发送UDP数据包。在网络层面，这些UDP包可能被代理的“TUN虚拟网卡”之外的路径直接发出，导致“直连”。
3.  **代码中硬编码**：开发者可能为了方便或追求更高性能，在代码中直接指定了 `aiodns` 要使用的DNS服务器，这进一步绕过了你系统的网络设置。

### 🤔 一个具体的例子

在Open WebUI的某个版本中，就出现了因为 `aiodns` 导致无法连接OpenRouter的问题。当时，`aiodns` 无法联系到DNS服务器，导致域名解析失败，所以 Open WebUI 无法连接到 OpenRouter。在卸载 `aiodns` 后，程序回退到使用标准的、能被代理正常处理的系统DNS解析器，问题就解决了。

### 💡 如何防止问题复发？

你提到的“最容易复发的坑”确实存在。为了避免它再次发生，你可以考虑以下方法：

*   **根本方法：指定代理环境变量**：这是最推荐的方式。在启动 Open WebUI 前，通过设置 `HTTP_PROXY` 和 `HTTPS_PROXY` 环境变量，强制所有网络请求（包括 `aiodns`）通过代理。
*   **预防方法：冻结依赖版本**：在 `requirements.txt` 或 `pyproject.toml` 中明确指定 `aiodns` 的版本（或不安装），可以防止后续安装其他包时将其作为依赖项一并安装。
*   **备选方法：配置TUN模式**：如果你的代理软件支持，可以尝试配置TUN模式的“DNS劫持”功能，强制将所有DNS请求转发给代理处理。但这可能配置较复杂。

### 💎 总结

`aiodns` 是一个“抄近道”的DNS解析器，它绕过系统API直接发DNS请求，所以你的TUN代理管不到它。

为了避免这个“坑”再次出现，**最佳实践是在启动Open WebUI时通过环境变量明确指定代理**，这是最可靠的方式。
